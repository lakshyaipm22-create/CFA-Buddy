# Study intelligence engine: spaced practice, gamification, review queue, and weekly reports

Four interlocking features turn CFA Buddy from a question bank into a daily study system. A spaced practice engine (/practice) uses SM-2 scheduling to surface questions weighted by subject weakness. A gamification layer (XP, levels, streaks, badges, exam readiness) wraps around the existing session data to provide motivation and progress tracking. A smart review queue (/review) unifies due flashcards, practice questions, and revision subjects into one flow. A weekly report (/weekly-report) generates trend analysis with pure SVG sparklines. All state lives in localStorage.

**Watch for:**
- Gamification state is computed and persisted inside `useMemo` on the dashboard, which is a side effect in a pure computation — React 19 strict mode may double-fire this, causing duplicate badge awards and XP drift (confirmed).
- The practice algorithm's `selectNextQuestion` calls `Math.random()` at render time via the `useState` lazy initializer chain, which violates React's purity contract and will produce hydration mismatches if SSR ever kicks in (confirmed).
- The topic heatmap performs an `O(sessions * attempts * allQuestions)` linear scan on every render to resolve question subjects — this will degrade noticeably once the user has hundreds of sessions (likely).
- No tests were added for any of the four features — 85 pre-existing tests pass, but the new 4,000 lines have zero coverage (confirmed).

## High-level view

The spaced practice engine adapts SM-2 for the full question bank with an 80/20 due-vs-new split weighted by per-subject accuracy. The subject accuracy computation requires loading all sessions from localStorage and scanning every attempt on each question pick, which will scale poorly as history grows.

Gamification lives entirely in a `useMemo` on the dashboard that recomputes state, checks badges, awards them, and writes back to localStorage — all within what React considers a pure function. This is the most architecturally fragile part of the change: a time bomb for strict mode and concurrent features.

The review queue aggregates three data sources into a day-gated flow. The queue is computed once on mount via `useMemo` and remains static for the session's lifetime — returning to the page mid-day won't pick up newly-due items.

The weekly report computes snapshots from session history with week-over-week deltas, but its CFA curriculum weights differ from those in the readiness score, so the two systems will give inconsistent subject prioritization.

## Side effects in React's pure computation layer

The dashboard's gamification computation is the riskiest architectural choice in this change. Inside `useMemo`:

```typescript
const gamificationData = useMemo(() => {
  // ...
  const updated = checkAndUpdateStreak(todayCount); // writes localStorage
  // ...
  if (newBadgeIds.length > 0) {
    const awarded = awardBadges(updated, newBadgeIds);
    saveGamificationState(awarded); // writes localStorage
    return { state: awarded, newBadgesEarned: true };
  }
  return { state: updated, newBadgesEarned: false };
}, [sessions, stats]);
```

`checkAndUpdateStreak` internally calls `saveGamificationState`, so localStorage is written on every recomputation. In React strict mode (which Next.js enables in development), this memo will fire twice per render. The second invocation sees the state from the first write, potentially double-counting or producing stale comparisons. Under concurrent features (transitions, Suspense boundaries), memos can be discarded and re-run, amplifying the problem.

The confetti trigger (`newBadgesEarned`) is derived from this same memo, so strict-mode double-fire would show confetti, then immediately "re-earn" the badge (no-op since it's already awarded), and the second render would see `newBadgesEarned: false` — confetti might flash and disappear.

## Practice algorithm's render-time randomness

`PracticeContent` initializes via:

```typescript
const [initialized] = useState(() => initQuestions());
```

`initQuestions` calls `selectNextQuestion`, which calls `Math.random()` multiple times for the weighted selection. This is the same pattern the confetti component deliberately avoided by using a seeded PRNG. The `useState` lazy initializer runs during the first render, so in strict mode it will run twice, potentially selecting different questions each time (though only the first result persists). If the page is ever server-rendered for a static shell, the server and client will produce different random values, causing a hydration mismatch.

## Heatmap performance cliff

The topic heatmap computes accuracy per reading:

```typescript
for (const session of completed) {
  for (const attempt of session.attempts ?? []) {
    const q = allQuestions.find(sq => sq.id === attempt.questionId);
    // ...
  }
}
```

`allQuestions.find` is O(n) and runs for every attempt across every session. With 1,000 questions and a few hundred sessions averaging 20 attempts each, that's 4,000+ find operations on a 1,000-element array — roughly 4 million comparisons. The fix is trivial: build a `Map<string, Question>` before the loop (the queue-builder already does this correctly).

## Two diverging streak systems

`practice-storage.ts` tracks a practice-specific streak that increments on first practice of the day regardless of count. The gamification system requires 10+ questions per day. These appear independently on the UI:

- Practice stats bar: "Streak: 5 days" (from `practice-storage`)
- Dashboard streak display: "3" (from `gamification-storage`)

A user who practices 5 questions daily will see their practice streak climb while their gamification streak stays at zero.

## Heatmap click → dead-end navigation

`TopicHeatmap` navigates to `/practice?subject=X&topic=Y` on cell click:

```typescript
const handleCellClick = useCallback((subject: string, reading: string) => {
  const params = new URLSearchParams({ subject, topic: reading });
  router.push(`/practice?${params.toString()}`);
}, [router]);
```

But `PracticeContent` and `practice-algorithm.ts` never read `searchParams`. The user lands on the practice page and gets a random question from any subject. The heatmap promises filtered practice but doesn't deliver it.

## Readiness score calibration factor penalizes non-users

When no sessions have confidence metadata (`certainTotal === 0`), the calibration factor contributes 0 to the composite score. Since calibration is weighted at 15%, a user who has never used the "Certain" confidence marker gets a permanent 15-point penalty. The score claims to be "0-100" but effectively caps at 85 for users who don't use confidence tagging, with no UI indication of how to unlock those points.

## Curriculum weights diverge across files

`report-generator.ts` defines:
```typescript
'Quantitative Methods': 10,
'Economics': 10,
'Equity Investments': 11,
'Fixed Income': 11,
```

`readiness-score.ts` defines:
```typescript
'Quantitative Methods': 0.08,
'Economics': 0.08,
'Equity Investments': 0.13,
'Fixed Income': 0.13,
```

The same subjects have different weights in two files. The weekly report uses these for focus suggestions ("13% of exam"), while readiness uses them for accuracy weighting. These should share a single source of truth. The readiness score weights match the official CFA Institute weights more closely; the report weights appear to be approximations that drift.
