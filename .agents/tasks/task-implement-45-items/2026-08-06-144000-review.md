# Full-stack CFA Buddy Phase 1: Security fixes and 10-feature implementation

This v2 review covers the same 12,000-line change after the coder addressed all 7 issues from the v1 review. Admin verification now checks `app_metadata.role === 'admin'` via a `requireAdmin()` helper. Flashcard update and delete actions include `userId` in the `where` clause. The search API caps query length at 200 characters. The ownership fix was applied selectively — flashcards are protected, but notes, mistakes, and sessions are not.

Watch for: notes/mistakes/session mutation actions still update by primary key without a `userId` filter, creating the same ownership bypass risk that was fixed for flashcards (confirmed); the 32-bit hash in `generateStableId` has a realistic collision window at scale that would silently merge distinct questions (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The ownership fix was not applied uniformly. The `updateNote`, `deleteNote`, `classifyError`, `resolveMistake`, and `completeSession` actions all mutate records by primary key without a `userId` filter. RLS protects the database layer, but the application layer relies on a single defense line — if the Prisma client ever connects via a service role or RLS is misconfigured, these actions become IDOR vulnerabilities. The flashcard actions demonstrate the correct pattern; the other mutation actions should follow it.

The `generateStableId` function for question imports uses a 32-bit integer hash. With ~2 billion distinct values, the birthday problem yields ~0.025% collision probability per 1000-question batch — acceptable for early use but a data-corruption risk as the question bank scales past ~50k items.

## Ownership asymmetry across mutation actions

The v1 review flagged that `reviewFlashcard` and `deleteFlashcard` updated by primary key alone. The fix correctly added a compound `where`:

```typescript
// flashcards.ts - fixed
await prisma.flashcard.delete({
  where: { id: validated.data.flashcardId, userId: userId! },
});
```

The same pattern was not applied to other mutation actions. In `notes.ts`:

```typescript
await prisma.note.update({
  where: { id: validated.data.noteId },
  data: { content: validated.data.content },
});
```

In `mistakes.ts`:

```typescript
await prisma.questionAttempt.update({
  where: { id: validated.data.attemptId },
  data: { errorClassification: validated.data.errorClassification },
});
```

In `questions.ts` (`completeSession`):

```typescript
await prisma.questionSession.update({
  where: { id: validated.data.sessionId },
  data: { status: 'Completed', completedAt: new Date(completedAt) },
});
```

All should add `userId: userId!` to the `where` clause.

## Import hash collision risk

The `generateStableId` function truncates to 32 bits:

```typescript
hash = ((hash << 5) - hash) + char;
hash = hash & hash; // Convert to 32bit integer
```

This produces `imp-{base36}` IDs with a maximum of ~2.1 billion distinct values. The birthday paradox gives: for N questions total, collision probability ≈ N²/(2 × 2^32). At 50k questions: ~0.03%. At 200k: ~0.5%. A collision means two distinct questions get the same ID — the second import silently overwrites (overwrite mode) or skips (default mode).

Fix: use `crypto.createHash('sha256')`, truncate to 16 hex characters (64 bits → collision at ~4 billion items), prefix with `imp-`.

## Sign-up action missing DB availability guard

In `sign-up.ts`, after successful Supabase auth:

```typescript
if (data.user) {
  try {
    const { prisma } = await import('@/shared/lib/prisma/client');
    await prisma.user.create({ ... });
  } catch (dbError) {
    console.error('Failed to create user record in database:', dbError);
  }
}
```

When no database is configured, this hits the stub proxy which throws "Database not configured" on every signup. The error is caught, but it generates log noise and wastes an import. Wrap with `if (isDatabaseAvailable())` like every other action.
