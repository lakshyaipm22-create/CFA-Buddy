# Full-stack CFA Buddy Phase 1: Auth, Data Layer, 10 Features

This change adds a complete full-stack implementation across 10 feature areas for a CFA exam study app: Supabase auth with middleware gating, Prisma schema with RLS policies, a dual-mode data layer (Postgres or localStorage fallback), Server Actions for all mutations, a question import pipeline, admin verification UI, rich-text notes, PDF viewer enhancements, error analytics, flashcard stats, animated transitions, cursor pagination, property tests, CI pipeline, and an onboarding flow. The architecture cleanly separates the DB-connected path from a localStorage fallback, meaning the app runs without any configured database.

Watch for: admin verification actions lack role-based authorization (confirmed); flashcard delete/update actions don't verify record ownership before mutating (confirmed); the search API route passes unsanitized user input into Prisma `contains` queries without length bounds (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The middleware implements a proper auth gate with Supabase SSR cookie handling, but gracefully bypasses all auth when environment variables are missing or set to placeholders. This dual-mode design is central to the app's offline-first story and works because the data layer similarly branches on `isDatabaseAvailable()`, which caches a boolean for the process lifetime. Every Server Action follows a consistent template: Zod validation, Supabase user check, `isDatabaseAvailable()` branch, Prisma call or localStorage fallback.

The schema models a full CFA curriculum hierarchy (Level > Subject > Reading > Topic > Concept) with RLS policies on all user-owned tables. Policies use a subquery pattern (`user_id IN (SELECT id FROM users WHERE auth_user_id = auth.uid()::text)`) which introduces per-row subquery cost that will matter at scale.

The admin question verification actions claim to "require admin access" in their JSDoc but perform no role check — any authenticated user can approve or reject questions. Similarly, the flashcard and question-attempt mutation actions verify the user is logged in but don't confirm ownership of the record being modified, relying entirely on RLS to enforce access control at the DB layer. If the app ever uses a service-role connection or the Prisma client bypasses RLS, this becomes an authorization bypass.

The search API route accepts arbitrary-length queries and passes them into Prisma `contains` filters and filesystem reads without sanitization or length capping, creating potential for expensive full-table scans.

The UI layer uses Framer Motion animations with a `prefers-reduced-motion` CSS override, 44px mobile touch targets, and Recharts charts loaded via `dynamic()` imports. Property tests cover SM-2, session recommender, and pagination invariants, but no integration tests exercise Server Actions, middleware, or RLS policies.

<details>
<summary>Issues (7)</summary>

1. **Admin verification has no role check** — `approveQuestion`, `rejectQuestion`, and `bulkApprove` verify the user is authenticated but never check for an admin role. Add a role/claim check before allowing verification operations.
2. **Flashcard actions don't verify ownership** — `reviewFlashcard` and `deleteFlashcard` update/delete by `id` without a `userId` filter in the `where` clause. Add ownership verification or use a compound `where` that includes `userId`.
3. **Search API accepts unbounded input** — The `/api/search` route doesn't cap query length or rate-limit. Add `query.slice(0, 200)` and consider a debounce or rate-limit at the API layer.
4. **RLS subquery pattern may be expensive at scale** — All RLS policies use `user_id IN (SELECT id FROM users WHERE auth_user_id = auth.uid()::text)` per row. Consider a `SECURITY DEFINER` helper function or a join-based policy once table sizes grow.
5. **`isDatabaseAvailable()` is permanently cached** — If the DATABASE_URL becomes available after cold start (e.g., environment variable rotation in a serverless function that persists across invocations), the cache never invalidates. Acceptable for current deploy targets but worth documenting.
6. **Exam countdown cross-tab sync removed** — The rewrite from `useSyncExternalStore` to `useState` lazy initializer means the component won't react to `localStorage` changes from other tabs. This aligns with the project's React rules but is a behavioral regression.
7. **CI pipeline doesn't run migrations** — The GitHub Actions workflow uses placeholder env vars and `npx prisma generate || true` but never runs migrations against a test database, so schema drift between code and migrations won't be caught.

## Admin verification authorization gap

The `verify.ts` file documents that `approveQuestion` "Requires admin access via Supabase auth" but the implementation only checks that `userId` is non-null:

```typescript
const supabase = await createServerSupabaseClient();
const userId = supabase
  ? (await supabase.auth.getUser()).data.user?.id
  : null;

if (isDatabaseAvailable() && !userId) {
  return { success: false, error: 'Authentication required.' };
}
```

No role check, no `app_metadata.role === 'admin'` guard. Any authenticated user who can reach `/admin/questions` (unprotected by any route-level guard beyond auth) can approve or reject any question. The admin page at `src/app/(protected)/admin/questions/page.tsx` has no server-side authorization check either.

## Record ownership in mutation actions

The flashcard `reviewFlashcard` and `deleteFlashcard` actions locate records by primary key alone:

```typescript
await prisma.flashcard.delete({
  where: { id: validated.data.flashcardId },
});
```

If the Prisma client connects via a role that bypasses RLS (common in migration/seed scripts, and possible if `DATABASE_URL` uses a service-role connection string), any user could delete another user's flashcard. The same pattern appears in `classifyError` for `questionAttempt.update`. Fix: add `userId` to the `where` clause.

## Search API input handling

The `/api/search` route accepts arbitrary query strings and uses them in:

- `prisma.question.findMany({ where: { questionText: { contains: query } } })` — triggers `LIKE '%...%'` scan
- `prisma.note.findMany({ where: { content: { contains: query } } })` — same
- Reads and parses the entire `content-index.json` into memory on every request

No maximum query length is enforced. A 10KB query string passes directly into Prisma's `contains` filter. Adding `if (query.length > 200) return NextResponse.json({ results: [] })` would be a minimal fix.

## Data layer caching behavior

The `isDatabaseAvailable()` function caches its result in a module-level variable for the process lifetime. This means a serverless function that starts without `DATABASE_URL` and later gets one (via config push) won't recover without a cold start. For Vercel's deployment model where env changes trigger redeployment, this is a non-issue in practice, but should be documented for other deploy targets.

## RLS policy performance

Every RLS policy uses the pattern:

```sql
CREATE POLICY "notes_select_own" ON "notes"
    FOR SELECT USING (user_id IN (SELECT id FROM users WHERE auth_user_id = auth.uid()::text));
```

This executes a subquery per row evaluated. The `users_auth_user_id_key` unique index helps, but at scale this will show up in `EXPLAIN ANALYZE`. A `SECURITY DEFINER` function that returns the internal `users.id` for the current `auth.uid()`, cached per-transaction, would allow a simple equality check: `user_id = get_current_user_id()`.

## Test coverage gaps

Not tested: Server Actions (no integration tests exercise the Zod validation + Prisma path), the search API route, middleware auth flow, RLS policies, or the content sync pipeline. The CI pipeline runs `npm run test` which covers unit/property tests only.

## CI pipeline schema drift risk

The workflow uses placeholder environment variables:

```yaml
env:
  DATABASE_URL: postgresql://placeholder:placeholder@localhost:5432/placeholder
```

All DB-dependent paths branch on `isDatabaseAvailable()` which returns false for placeholder URLs, so type-check, lint, build, and unit tests pass. However, schema changes that don't match the Prisma client or migration SQL won't surface until a real database is connected.
