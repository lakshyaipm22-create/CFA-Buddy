# Analytics dashboard for CFA Buddy test sessions

A comprehensive analytics feature spanning four sub-features: a computation engine with session processing and filtering, a test history dashboard at `/analytics`, an individual session deep-dive at `/analytics/session/[sessionId]`, trend visualizations (accuracy over time, time efficiency, confidence calibration, subject progression), auto-generated smart insights, a session comparison mode, and loading skeletons. All data sourced from localStorage. Recharts lazy-loaded throughout. 59 new unit tests cover the computation layer.

**Watch for:** The `ComparisonCard` component's `goodDirection` parameter is dead code — both branches of the ternary evaluate identically, so the "down-is-good" logic for time/question and guess rate metrics is broken (confirmed). The confidence breakdown bar in `SessionCard` mixes asymmetric semantics: `certainCorrect` is an intersection (confident AND correct) while `thinkSo` and `guess` are totals regardless of correctness, making the percentages not sum to 100% and misrepresenting confidence distribution (confirmed). The subject-level comparison in `SessionComparison` only works when both sessions are single-subject; mixed-mode sessions produce no per-subject data (confirmed).

## High-level view

The computation layer (`analytics-engine.ts`, `trend-engine.ts`, `insights-engine.ts`, `time-utils.ts`) processes raw `QuestionSession` objects into typed `AnalyticsSession` records, computes aggregate stats, filters/sorts, computes trends over time, and generates up to 5 heuristic-based insights. Trends group by calendar day, meaning a user who takes multiple sessions in one day sees their results averaged rather than individually plotted.

The session analysis page (`session-analysis.tsx`, ~1200 lines) loads three data sources synchronously via `useState` lazy initializers (session, all sessions, all questions) and computes a massive derived `analysis` object in a single `useMemo`. A `ComparisonCard` bug makes directional indicators incorrect for metrics where lower-is-better.

The session comparison mode allows selecting two sessions from the card grid for side-by-side comparison. Its per-subject comparison is limited to session-level subject metadata rather than per-question subject classification, producing meaningful data only when comparing two single-subject tests on the same subject.

## ComparisonCard direction bug

In `session-analysis.tsx` (lines ~1173-1174):

```typescript
const isGood = goodDirection === 'up' ? diff > 0 : diff > 0;
const isBad = goodDirection === 'up' ? diff < 0 : diff < 0;
```

Both branches of each ternary are identical. The intended behavior is that for `goodDirection: 'down'` (e.g., time per question, guess rate), a *negative* diff should show green and a *positive* diff should show red. Currently, "Time/Question" going up still shows green. The caller compensates partially by negating `diff` at the call site (`diff={-timeDiff}`) — but this inverts the arrow direction too, so TrendingUp shows when time decreased, which is semantically confusing in combination with the dead `goodDirection`.

## Confidence breakdown asymmetry in SessionCard

The `ConfidenceBreakdown` type defines:
- `certainCorrect`: count of attempts where confidence=Certain AND correct=true
- `thinkSo`: count of ALL attempts where confidence=ThinkSo (correct or not)
- `guess`: count of ALL attempts where confidence=Guess (correct or not)

The session card renders these as a stacked bar with total width = totalQuestions. But `certainCorrect + thinkSo + guess` doesn't equal `totalQuestions` — the remaining `Certain` answers that are incorrect are unaccounted for in the bar. This means the bar will have a gray gap representing "Certain but wrong" answers, which may confuse users expecting a complete breakdown.

## Subject comparison limited to session-level metadata

`SessionComparison` builds per-subject stats from `earlier.subject` and `later.subject`, which are session-level fields from the session config. For a `Mixed` mode session, these are `null`. The component has access to `rawA` and `rawB` (the full session objects with attempts), and could iterate attempts to build per-question subject data by looking up each question's subject — but currently does not.

## Session analysis synchronous load cost

The `analysis` useMemo touches all sessions (not just the current one) to compute personal averages. `loadAllQuestions()` parses up to 1,878 questions from localStorage synchronously in a lazy initializer. With the 30-day / 50-session auto-cleanup, the data volume is bounded, but there's no module-level caching — navigating between session analysis pages re-parses the full question bank each time.

## Test coverage gaps

Not tested: the UI components themselves (no component/integration tests), the confidence breakdown asymmetry (tests create mock `AnalyticsSession` objects directly rather than going through `computeSessionStats`), the ComparisonCard rendering logic, or the lazy-loading behavior of Recharts wrappers.
