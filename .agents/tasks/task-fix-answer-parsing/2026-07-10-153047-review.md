# Multi-format answer parsing for CFA import pipeline (v2)

The import pipeline's answer parser (`parseSolutions` in the CLI script and `parseAnswers` in the utility module) was rewritten from a single-regex approach to a block-split-then-probe architecture that handles four CFA answer formats: "C is correct", "C.", "C " (letter + space), and "C\n" (letter alone on line). The v1 review raised three issues — fragile `isDirectExecution` guard, lookahead divergence between parsers, and unreachable final pattern — all of which are now fixed.

**Watch for:** The two parsers still use fundamentally different block-splitting strategies (two-phase index slicing vs. single-regex lazy match), which can produce different block boundaries on edge-case input (likely). The `question-parser.ts` block regex uses a lazy quantifier `[\s\S]*?` terminated by a lookahead, which can silently truncate explanation text if the lookahead fires mid-explanation on a line matching `\n\s*\d+\s*[.)]` (confirmed).

**Verdict**: APPROVED

## High-level view

All three v1 issues are resolved: unified `(?!(?:is\s+)?correct)` lookahead, `[ \t]+` making the final pattern reachable, and `import.meta.url` for the execution guard.

The one remaining asymmetry is architectural: `parseSolutions` splits blocks by finding all start positions and slicing between them (greedy — captures everything until the next block start), while `parseAnswers` uses a single regex with `[\s\S]*?` (lazy — captures as little as possible before the lookahead). For most CFA content these produce identical results, but a multi-paragraph explanation containing a line like "  42. percent of..." would be truncated by the lazy approach in `parseAnswers` while `parseSolutions` would correctly include it.

## Block-splitting divergence

`parseSolutions` in `import-questions.ts`:
```ts
const blockPattern = /(?:^|\n)\s*(\d+)\.\s+/g;
// finds all start positions, then slices text[start[i]..start[i+1]]
```

`parseAnswers` in `question-parser.ts`:
```ts
const answerPattern = /(?:^|\n)\s*(\d+)\s*[.)]\s*([\s\S]*?)(?=(?:\n\s*\d+\s*[.)])|$)/g;
```

The utility's regex terminates each block at the lookahead `(?=\n\s*\d+\s*[.)])`. If an explanation contains "see section 3. for details", the lookahead fires at "3." and truncates the explanation — capturing only up to that point, then starting a new (likely unparseable) block at "3.". The script's two-phase split has the same vulnerability in theory (it also matches on `\d+\.\s+`), but requires a newline before the digits and at least one whitespace after the period, which is slightly more restrictive.

Both parsers would benefit from a minimum question-number heuristic (e.g., only split on numbers ≤ the expected question count), but that's a future hardening concern rather than a bug introduced by this PR.

## Test coverage gaps

Not tested: the block-splitting edge case described above; behavior when `parseSolutions` is called on text that has no `SOLUTIONS` header (it parses whatever numbered blocks it finds, meaning the function's contract is broader than its name implies).
