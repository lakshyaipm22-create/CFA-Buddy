# Multi-format answer parsing for CFA import pipeline

The import pipeline's answer parser (`parseSolutions` in the CLI script and `parseAnswers` in the utility module) previously only matched the format "X is correct. Explanation..." — which left Fixed Income (132 questions), Alternative Investments (65), and Derivatives (45) with zero or near-zero correct-answer hits because those PDFs use terse formats like "C. Explanation" or "C Explanation". This change rewrites both parsers to use a two-phase approach: split text into numbered blocks first, then try four regex patterns in priority order against each block's content.

**Watch for:** The `isDirectExecution` guard that prevents the CLI script from auto-running during tests relies on `process.argv[1].includes('vitest')` — a heuristic that breaks if the test runner binary path changes (confirmed). Pattern 4 in `import-questions.ts` uses a narrower negative lookahead than the same logical pattern in `question-parser.ts`, creating a subtle behavioral asymmetry between the two parsers (confirmed).

## High-level view

Both parsers were rewritten from a single-regex approach to a block-split-then-probe architecture. The block splitting uses `\d+\.\s+` boundaries, decoupling block detection from answer-format matching. The four probe patterns cascade in specificity: "is correct" → "letter + period" → "letter + space + text" → "letter alone on line".

The two parsers implement the same logic independently rather than sharing code. They diverge in one detail: the negative lookahead that prevents the "letter + space" pattern from stealing content meant for the "is correct" pattern. The utility version excludes both "is correct" and bare "correct"; the script version only excludes "is correct". This doesn't cause a bug today (Pattern 1 runs first), but the implementations may drift further over time.

The test suite adds 21 new tests covering all four format variants, mixed-format inputs, multi-digit question numbers, and multiline explanations. The notable gap is the lack of any test for the `isDirectExecution` guard.

## Pattern cascade and the unreachable final pattern

The four patterns cascade:

```
Pattern 1: /^([A-D])\s+is\s+correct[.]?\s*([\s\S]*)/i     → "C is correct. ..."
Pattern 2: /^([A-D])\.\s+([\s\S]*)/                         → "C. ..."
Pattern 3: /^([A-D])\s+(?!is\s+correct)([\s\S]*)/i          → "C Explanation..."
Pattern 4: /^([A-D])\s*\n([\s\S]*)/m                        → "C\n..."
```

Pattern 3's `\s+` includes `\n` in JavaScript. Content like `"C\nExplanation..."` matches Pattern 3 — the `\s+` consumes the newline, the lookahead passes because "Explanation" doesn't start with "is correct". Pattern 4 can only fire if there's zero whitespace between the letter and the newline, but that's the same single-`\n` case that Pattern 3's `\s+` already matches.

If Pattern 3's lookahead were ever tightened (e.g., requiring non-whitespace after `\s+`), Pattern 4 would become load-bearing without any test proving it works in isolation.

## Negative lookahead asymmetry

In `import-questions.ts`:
```js
const p3 = content.match(/^([A-D])\s+(?!is\s+correct)([\s\S]*)/i);
```

In `question-parser.ts`:
```js
const p4 = content.match(/^([A-D])\s+(?!(?:is\s+)?correct)([\s\S]*)/i);
```

The utility version additionally rejects content starting with bare "correct" (no preceding "is"). If a PDF contained `"A correct answer is..."` as explanation text after a letter, the utility would skip it (falling through to Pattern 5, which is unreachable — so it would produce no match at all) while the script would match letter "A" with explanation "correct answer is...". Two functions that should behave identically have a hidden semantic difference that could silently drop answers in one path but not the other.

## `isDirectExecution` guard

```ts
const isDirectExecution = typeof process !== 'undefined'
  && process.argv[1]
  && !process.argv[1].includes('vitest');
```

This fails if: (a) tests are run through a wrapper script, (b) the project migrates to a different test runner, (c) vitest is invoked via `npx` with a versioned path that doesn't contain the literal string. The standard ESM idiom is:

```ts
import { fileURLToPath } from 'url';
if (process.argv[1] === fileURLToPath(import.meta.url)) { main(); }
```

The current guard also wouldn't prevent execution if the file were imported from a non-test script (e.g., another CLI tool importing `parseSolutions`).

## Test coverage gaps

Not tested: the `isDirectExecution` guard behavior; the interaction between `parseProblems` and `parseSolutions` when block boundaries overlap (e.g., a solution explanation that contains "2. " mid-sentence, which would split the block prematurely); content where the answer letter is lowercase (the `i` flag is applied inconsistently — Pattern 2 in both parsers is case-sensitive for the letter `[A-D]` while Patterns 1 and 3 use the `i` flag on the full regex but the character class `[A-D]` itself doesn't match lowercase regardless of `i`).
